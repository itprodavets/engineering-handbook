# I/O-bound и CPU-bound — точные определения

[Русский](io-vs-cpu-bound.md) · [English](en/io-vs-cpu-bound.md)

[Главная](../../../README.md) · [Модуль](../async-lifecycle.md) · [Все разделы](README.md) · [Платформа](https://itprodavets.github.io/engineering-handbook/#/ru/unit/io-vs-cpu-bound)

> Различать вычисление, ожидание сети и физические ресурсы.

## Определение

I/O-bound — операция, задержка или пропускная способность которой определяется внешним вводом/выводом. CPU-bound ограничена скоростью исполнения инструкций. Вызов PostgreSQL включает как CPU-работу, так и сетевое ожидание.

## Внутренний механизм

1. До отправки SQL процессор выполняет код EF Core/Npgsql и сериализацию сетевого запроса.
2. При незавершённом асинхронном ожидании worker не закреплён за запросом; ОС может выполнять другие потоки.
3. После получения данных CPU снова нужен для чтения, декодирования, материализации объектов и ответа HTTP.
4. Async не делает PostgreSQL быстрее: пулы соединений, БД и объём результата остаются ограничениями.

## Последовательное объяснение

### Время ожидания не равно времени CPU

Полное время запроса состоит из вычислений клиентского приложения, ожидания сети/БД и обработки ответа. Пять секунд SQL не означают пять секунд CPU на сервере ASP.NET Core: во время незавершённого асинхронного ожидания worker может работать над другой задачей. Однако EF Core и драйвер всё равно используют CPU при построении SQL, передаче данных, декодировании и создании объектов.

### Ожидаем операцию, а не освобождение конкретного CPU

Рабочий поток .NET — это поток ОС, который планировщик размещает на логическом CPU. `await` сам по себе не освобождает «ядро №3»: при незавершённой операции async-метод регистрирует продолжение и возвращает управление. Поток может брать другую работу, а ОС решает, на каком CPU он будет выполняться. При завершённой Task приостановки может не быть.

### Какие ресурсы ограничивают масштабирование

Для 1 000 HTTP-запросов необходимо различать количество запросов, активных DB-соединений, выполняемых SQL, заблокированных workers и ожидающих Task. Пул PostgreSQL-подключений может ограничить одновременно выполняемые запросы задолго до исчерпания ThreadPool. `ToListAsync()` также удерживает память под результаты; полезно ограничивать выборку и применять пагинацию.

### Что можно проверить

Для конкретного процесса фиксируй: CPU time, `dotnet.thread_pool.thread.count`, `dotnet.thread_pool.queue.length`, число DB-соединений и latency p95/p99. Эти показатели измеряют разные ресурсы. Низкий CPU при росте очереди — сигнал для диагностики, но ещё не доказательство ThreadPool starvation.


## Потребляемые ресурсы

CPU-время до/после ожидания; буферы и сокет во время I/O; 0 специально заблокированных worker для корректного pending async-read.

## Ошибки и ограничения

Не считай Database I/O отдельным видом аппаратной работы: удалённый PostgreSQL обычно означает Network I/O на клиенте.

## Пять уровней понимания

Сначала ответь самостоятельно. Критерии открой только после попытки.

### 1. Recall

Что означает I/O-bound? Назови два конкретных ресурса, которые могут ограничивать запрос к PostgreSQL.

<details>
<summary>Критерии ответа</summary>

Указаны задержка/пропускная способность I/O и конкретные примеры: сеть, DB connection pool, throughput БД. Не путать с вычислениями CPU.

</details>

### 2. Explain

Расскажи, что выполняет CPU до, во время и после await ToListAsync().

<details>
<summary>Критерии ответа</summary>

До: подготовка/отправка; при незавершённом I/O: worker не закреплён за запросом; после: чтение/материализация/HTTP. Не утверждай, что CPU всё время простаивает.

</details>

### 3. Predict

Если SQL выполняется 5 секунд, будет ли HTTP worker заблокирован на эти 5 секунд при корректном async I/O?

<details>
<summary>Критерии ответа</summary>

Нет, при незавершённом асинхронном ожидании. Но операция может завершиться синхронно и CPU всё равно нужен при обработке ответа.

</details>

### 4. Diagnose

При 1 000 запросов CPU=25%, p99 latency растёт. Почему нельзя сразу обвинять ThreadPool? Что измеришь?

<details>
<summary>Критерии ответа</summary>

Проверить thread count, очередь и stacks, DB connection pool, SQL plans, latency, downstream limits. Низкий CPU неоднозначен.

</details>

### 5. Design

Как ограничить число одновременных запросов к базе, не блокируя worker-потоки?

<details>
<summary>Критерии ответа</summary>

Асинхронный SemaphoreSlim.WaitAsync или Channel с bounded capacity, release/finally, CancellationToken, таймауты и наблюдаемость; не использовать sync Wait.

</details>
